# GUI выделенного стенда привязок

## Запуск

Из `C:\development\BoilerRoomSimulator` запустить
`C:\Tools\Python311\python.exe web_bindings_gui.py`.

Окно использует Tkinter/ttk и Canvas, не wxPython. Дополнительные пакеты для GUI
не нужны, если используемый Python установлен с Tcl/Tk. Для рабочего процесса
нужны обычные зависимости приложения, в частности python-can и CAN-backend.

## Что реализовано

- Настройки четырёх устройств, HTTP-доступа и подключения CAN/UDP.
- Редактирование таблиц резисторных входов и обратной связи реле.
- Автоматическая схема: контроллеры, расширения, I²C/CAN, обратные связи,
  управление питанием. Перетаскивания нет.
- Сохранение и восстановление профиля, включая логин и пароль.
- Read-only проверка доступности всех четырёх узлов по CAN и HTTP.
- Последовательный запуск существующих web-сценариев в отдельном процессе,
  журнал, результаты и штатная остановка.

**Это инфраструктура стенда, а не реализация всех пунктов 2.2.**
Пункты без сценарных файлов отображаются как «Не реализован» и не запускаются.
Сейчас доступны 9.1.1 и 9.1.2: проверки локальных привязок через HTTP с независимым
CAN-чтением. Они не проверяют температуры, физические контакты и перезагрузку.
Параметры резисторов, обратной связи и питания сохраняются для следующих сценариев;
в этой версии питание не переключается, ручные режимы не включаются.
PWM/0–10 V вне покрытия.

## Настройка

### Устройства

| Ключ профиля | Назначение |
| --- | --- |
| `dut_controller` | Тестируемый SWK с резисторами на входах |
| `dut_extension` | Его первый SWK_1 с резисторами на входах |
| `aux_controller` | Независимо питаемый вспомогательный контроллер |
| `aux_extension` | Первый SWK_1 вспомогательного контроллера |

Указать CAN ID всех четырёх узлов явно. ID различны, диапазон 1..255.
Для каждого расширения проверяется ID головного контроллера + 1;
после 255 ожидается 1, как в прошивке. Совпадения ID недопустимы.
Вспомогательный контроллер должен поддерживать I²C-расширение.
Прошивка должна представлять блок отдельным CAN-устройством SWK_1,
а не использовать `CFG_EXTENDED_CONTROLLERS_SIMPLE`.

Неизвестные ID в черновике можно оставить равными 0, но такой профиль не запускается.
Физические имена узлов постоянны: будущая рокировка владельца тестовой программы
не должна изменять CAN ID в настройках.

### Web и транспорт

Web URL — origin встроенного HTTP-сервера, например `http://192.168.1.50:8080`.
Не указывать `/rest.php`, логин/пароль в URL, query или fragment.
Шлюз может находиться на любом доступном контроллере и должен видеть все четыре узла.
Логин, пароль и HTTP timeout задаются отдельно.

Режим `can`: указать аппаратный context из `can.ini`.
Режим `udp`: указать порт существующего CAN-over-UDP моста; для внутреннего
CAN-интерфейса рабочего процесса применяется context `virtual`.
Веб-IP не фильтрует CAN/UDP-сегмент. Использовать только изолированный стенд
с уникальными CAN ID и программными ID.

### Разводка

Все номера каналов в GUI и JSON **начинаются с 1**: R1, S1 и т.д.
Протокольные индексы существующих сценариев остаются нулевыми.

Резисторный вход: устройство, номер S, ожидаемая температура в °C и допуск.
Разные номиналы позволяют различать источники. Минимальный полный профиль
требует резисторный вход на SWK и на его расширении.

Обратная связь: устройство-источник, номер R, устройство-наблюдатель, номер S,
и признак «КЗ при ON» (True — нормально разомкнутый контакт).
Например: SWK R1 → aux S1; первый SWK_1 R1 → вспомогательный SWK_1 S1.
Каждая связь задаётся явно, автоматического правила Rn → Sn нет.
Минимальный профиль требует обратную связь хотя бы одного выхода SWK
и одного выхода его расширения. Один вход нельзя одновременно использовать
для резистора и обратной связи; дубликаты реле и входов запрещены.
Подключаются только подходящие сухие контакты без внешнего напряжения
на измерительных входах.

Служебное реле питания принадлежит aux-контроллеру и не может быть тестируемым
выходом. Задаются номер R, команда отключения (0 или 255), длительность отключения
и время ожидания запуска. Его электрическая схема, независимое питание aux-пары
и механизм возврата питания при потере связи проверяются отдельно.
**Read-only проверка не доказывает правильность разводки или схемы питания.**

## Сохранение

«Сохранить» записывает `web_binding_bench_settings.json` рядом с точкой запуска.
При запуске проверки профиль также сохраняется; закрытие предлагает сохранение.
Файл заменяется атомарно, ошибка чтения/версии видна в окне. Повреждённый профиль
не заменяется без отдельного подтверждения. Поддерживается версия схемы 1.

Логин и пароль сохраняются **открытым текстом**, по условиям тестового стенда.
Файл исключён из Git. HTTP-сессии не сохраняются.

Для рабочего процесса создаётся отдельный временный снимок профиля, удаляемый
после завершения. Пароль не передаётся в аргументах процесса. Редактирование полей
во время прогона заблокировано; запущенный процесс использует свой снимок.

## Проверка и запуск

1. Заполнить настройки и таблицы. Проверить схему и сохранить профиль.
2. Нажать «Проверить стенд». Проверяются живые CAN-ответы о типе и числе каналов,
   тип SWK_1 у расширений, достаточность каналов для разводки и видимость узлов
   через HTTP. Пресеты не загружаются, питание не переключается.
3. На вкладке сценариев выбрать только реализованные проверки (Ctrl/Shift).
4. Нажать «Запустить» и заново подтвердить выделенный стенд без реальных нагрузок.
   Исходные программы тестируемого SWK будут удалены пресетом `web_bindings`.
   Их восстановления нет; конфигурация вспомогательного контроллера не сбрасывается.
5. Результаты появляются в таблице; сведения HTTP/CAN — в журнале.

Для стендового процесса отключена загрузка последнего/стартового пресета.
Перед запуском выполняется preflight; web-сценарий повторяет его перед своим
разрушительным сбросом. Существующая проверка конфликта программного ID 101
остаётся обязательной.

«Остановить» отправляет штатный запрос остановки, не убивает процесс.
Закрытие активного окна ожидает очистки приложения. Потеря stdin со стороны GUI
также считается запросом остановки. HTTP/CAN timeout может задерживать завершение;
окно остаётся отзывчивым. Принудительное завершение ОС не гарантирует очистки.

CLI приложения также принимает `--no-gui --web-bench <путь>`.
Для явного пути web-сценария нужен `--confirm-web-bench`; `all`, сторонние
сценарии, стартовый пресет и параллельные workers в этом режиме запрещены.
Управление несколькими запусками и автоматическое завершение обеспечивает GUI.
