# Проверка web-привязок в CAN-системе контроллеров

Для отдельного четырёхузлового стенда доступен
[GUI настройки и запуска](web_binding_bench_gui.md) на Tkinter.
Его профиль не расширяет покрытие существующих 9.1.1/9.1.2 до всех пунктов 2.2.

## Что проверяется

Сценарии отправляют JSON POST на **встроенный** `/rest.php` web-сервера
контроллера, затем независимо читают фактические привязки через CAN.
CAN можно подключить напрямую или через существующий UDP-мост.
Web-сервер — шлюз распределённой системы: он показывает контроллеры и программы
CAN-сети, включая собственные, и меняет привязки CAN-командами.
`--web-url` задаёт адрес этого шлюза, `--id` — CAN-ID тестируемого узла.
Это может быть один и тот же контроллер или разные контроллеры.
Тип тестируемого узла не ограничен XHCC: допустим, например, SWK.
Браузер, JavaScript сайта и облачный сервер teplomonitor в этих тестах не участвуют.
Файлы `web/teplomonitor-server/config.php` изменять не нужно.

| ID | Сценарий | Последовательность |
| --- | --- | --- |
| 9.1.1 | Web: привязка входа программы | Вход программы 0 → локальный вход 0; повтор; перепривязка → вход 1; отвязка; повторная отвязка |
| 9.1.2 | Web: привязка реле контроллера | Реле 0 → выход программы 0; повтор; перепривязка → выход 1; отвязка; повторная отвязка |

Все индексы здесь **с нуля**: вход 0 и реле 0 обычно отображаются как первый
вход и первое реле в пользовательском интерфейсе.
После каждого шага читаются все 4 входа и 5 выходов тестовой программы,
а также все реле выбранного контроллера (их число читается через CAN).
Проверяются ожидаемые изменения и неизменность
остальных привязок. Для реле проверяется и обратная привязка выхода программы.
Значения датчиков, срабатывание реле и сохранение привязок после перезагрузки
в этот первый набор не входят.

## Подготовка стенда

1. Использовать стендовые контроллеры или Qt-симуляторы **без реальных нагрузок**.
   Для тестируемого узла 9.1.1 нужны минимум два физических входа,
   для 9.1.2 — минимум одно реле. Число каналов определяется через CAN,
   фиксированного требования 18/11 нет. Например, для сборки `xhcc_s62`
   из `C:\development\SmartWeb`:

   ```powershell
   C:\Tools\Python311\scripts\scons.exe qtsim CFG_PROJECT=xhcc_s62 CFG_PLATFORM=qtsim --jobs=8
   ```

2. Запустить выбранные симуляторы или контроллеры. Для примера выше бинарник
   находится в `bin/xhcc_s62/`. Проверить IP-адрес и HTTP-порт web-шлюза,
   CAN-ID тестируемого узла и доступ к CAN (напрямую или через CAN-over-UDP).
3. Отключить VPN, если он блокирует доступ. Открыть локальные web-страницы
   контроллера и проверить вход `admin/admin`.
4. Использовать изолированный стендовый CAN-сегмент с уникальными CAN-ID.
   Несколько узлов допустимы; текущие сценарии настраивают только узел `--id`.
   UDP-мост использует broadcast-обнаружение и может подключать несколько узлов.
   Один лишь web-IP **не фильтрует UDP-трафик**. Совпадение ID в HTTP/CAN —
   дополнительная проверка, не уникальный аппаратный ID.
   ID программы 101 не должен использоваться на другом узле: CAN-команды
   программы адресуются её ID, без ID контроллера-владельца.
5. Запустить нужный web-сценарий в Симуляторе Котельной.
   Перед каждым запуском сценарий автоматически загружает пресет `web_bindings`:
   **удаляет текущие программы контроллера** и создаёт одну программу
   `DOUBLE_PUMP`, ID 101, без привязок и без виртуальных контроллеров I/O.
   Исходная конфигурация не сохраняется и не восстанавливается.

Вручную выбирать пресет или указывать `--preset web_bindings` не нужно.
Даже при уже выбранном `web_bindings` каждый запуск начинает с чистой конфигурации.
Перед сбросом проверяются наличие HTTP-настроек, ID контроллера, число каналов
по CAN, авторизация, видимость выбранного узла через web-шлюз и отсутствие
конфликта ID программы 101 на других узлах. Сессия подготовки закрывается
до загрузки пресета. После загрузки сценарий ждёт подтверждения её успешного
завершения и проверяет наличие тестовой программы. Перед HTTP-командами повторно
проверяются её ID и тип в выбранном контроллере HTTP-конфигурации, отсутствие
конфликта ID на других узлах и конфликтующих начальных привязок.
Наличие других контроллеров и программ в web-конфигурации само по себе не ошибка.

## Запуск

Пример: web-адрес `http://192.168.1.50`, CAN-ID 7, UDP-порт 31987.
Заменить эти значения фактическими; автоматически они не угадываются.
Команды выполняются из корня `C:\development\BoilerRoomSimulator`.

Первый сценарий без GUI:

```powershell
Set-Location C:\development\BoilerRoomSimulator
C:\Tools\Python311\python.exe main.py --no-gui --can virtual --udp 31987 --id 7 --profile web_tests --web-url http://192.168.1.50 --scenario C:\development\BoilerRoomSimulator\scenario\list\web\scenario_web_input_9_1_1.py
```

Второй сценарий:

```powershell
C:\Tools\Python311\python.exe main.py --no-gui --can virtual --udp 31987 --id 7 --profile web_tests --web-url http://192.168.1.50 --scenario C:\development\BoilerRoomSimulator\scenario\list\web\scenario_web_relay_9_1_2.py
```

Для GUI убрать `--no-gui`. Можно выбрать оба сценария в диалоге сценариев
и выполнить последовательно в одной сессии; каждый сам подготовит контроллер.
Прямой CAN: заменить `--can virtual --udp 31987` на нужный `--can <context>`.

По умолчанию используются логин `admin` и пароль `admin`.
Для другого пароля задать переменную окружения `BRS_WEB_PASSWORD` перед запуском;
имя переменной можно изменить через `--web-password-env`.
Логин меняется через `--web-login`, HTTP-таймаут — через `--web-timeout`
(по умолчанию 10 секунд, больше внутреннего 5-секундного ожидания прошивки).
URL может содержать HTTP-порт, например `http://192.168.1.50:8080`.
Пароль и session ID не выводятся в журнал. HTTP-прокси ОС не используются;
это не устраняет блокировку маршрутов VPN. Редиректы запрещены.
HTTP без TLS передаёт учётные данные открыто: использовать только доверенный стенд.

`--web-url` необязателен для обычных сценариев. Web-сценарии без него завершатся
ошибкой подготовки, ничего не меняя. Не выбирать `all` для обычного прогона,
если web-стенд не подготовлен. Web-тесты пока не поддерживают параллельный
координатор (`--can-ports`/`--udp-ports`) и отладочный ответчик `--debug`.

## Результат и состояние стенда

В консоли выводятся HTTP-шаг, подтверждение CAN и итог `9.1.1: OK/FAIL`
или `9.1.2: OK/FAIL`. При несовпадении выводятся канал и два сырых значения:
`expected=0x...., CAN=0x....`.

Снимок привязок после подготовки пресета используется только для проверки
неизменности остальных каналов. **Восстановления нет** ни после успеха,
ни после ошибки, ни после отмены. При успехе тестируемая привязка заканчивает
последовательность двойной отвязкой. При ошибке или отмене остаётся фактическое
состояние на момент остановки. Следующий запуск заново сбрасывает и готовит
выбранный узел. Ручные входы и аварийные сигналы эти сценарии не устанавливают.

HTTP-таймаут может произойти после применения команды. В этом случае выполняется
диагностическое CAN-чтение, но HTTP-команда автоматически
не повторяется, а результат остаётся `FAIL`.
Ошибка logout также не позволяет выставить `OK`.

В GUI отменять тест штатной остановкой сценария. После отмены или потери связи
нужно заново подготовить узел перед продолжением тестов, например повторным
запуском сценария. Автоматического отката нет.
В headless-режиме приложение остаётся работать после сценария;
нажимать Ctrl+C после итогового результата и завершения HTTP-сессии.
Код завершения обычного headless-приложения не является отчётом сценария.

## Офлайн-проверки

```powershell
Set-Location C:\development\BoilerRoomSimulator
C:\Tools\Python311\python.exe -m unittest tests.test_web_client tests.test_mapping_client tests.test_web_binding_scenarios -v
C:\Tools\Python311\python.exe tools\validate_scenarios.py
```

Тесты используют локальный HTTP-сервер и подменённый CAN, не внешний контроллер.
Они проверяют автоматическую подготовку пресета, разные количества каналов,
распределённую web-конфигурацию, конфликт ID программы до сброса, формат команд,
авторизацию, таймауты, отсутствие повторов HTTP-команд, обратные связи,
отмену и отсутствие восстановления.
Это не заменяет сетевой прогон
с реальной прошивкой; его нужно выполнить отдельно на доступном стенде.
Межконтроллерные привязки будут проверяться отдельными сценариями; текущие
9.1.1 и 9.1.2 работают с программой и I/O одного выбранного узла, даже если
web-шлюз находится на другом контроллере. Будущие межконтроллерные сценарии
должны подготавливать и сбрасывать обоих участников без последующего восстановления.
